Fixture & Empty State Plan

Architecture decisions for sql-workbench component

1. Fixture Format (v1 — keep as-is)

// One file per fixture at fixtures/<id>.json
{
  "id": "ecommerce",
  "kind": "sqlite-dataset",
  "version": 1,
  "title": "E-commerce sample",
  "reset": {
    "sql": "CREATE TABLE ... ; INSERT INTO ..."
  }
}

Agents write SQL fluently. The format matches how they think. Builder UI can parse SQL to render grids — no format change needed.

2. Empty State — Responsibility Split

/* Component boots empty (no dataset attr) */
Component → state-change { tableCount: 0 }
/* Host renders its own empty UI */
Host → show "Create a table or load data"

/* User runs CREATE TABLE */
User → Component: run("CREATE TABLE ...")
Component → state-change { tableCount: 1 }
/* Host hides empty UI */
Host → hides empty state

3. Component Tree

<HostPage>
  <sql-workbench
    onStateChange={...}
  /> ← owns state, emits events
  <EmptyState
    visible={tableCount === 0}
    cta="Load sample data"
  /> ← owns presentation
</HostPage>

4. Responsibility Split

Component (sql-workbench) Host (learn-tool, standalone, etc.)
Track tableCount Decide what empty looks like
Emit state-change event Write the copy
Run SQL, manage schema, journal Choose the CTA (load fixture, tutorial, etc.)

Same pattern as theme: component reads, host owns. Component stays deep (small interface, lots of behaviour). Embedders compose their own UX.
